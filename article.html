From a 72-Hour Prototype to a Privacy Incident: What Went Wrong and How to Rebuild It Right

A technical reflection on secure design principles, responsible development, and obligations under RA No. 10173.

By John • July 2026 • 10-minute read
🔒

Build fast.
Do not break trust.

Security and privacy must be part of the design.

A working prototype is not automatically a safe product. The students in this case successfully demonstrated what modern development tools can accomplish. With the help of an artificial intelligence coding assistant, they built a mobile-and-web platform in less than 72 hours.

The platform allowed student organizations to manage their members, collect event fees, communicate privately, and upload files. It worked well enough to win a hackathon prize and attract more than a dozen student organizations.

The main problem was not simply that the students moved quickly. The larger problem was that a hackathon prototype quietly became a production system without undergoing the security, privacy, testing, and operational changes required for real software.

Once the platform began storing full names, student numbers, phone numbers, GCash transaction screenshots, identification photos, and private messages, the developers were no longer handling harmless demonstration information. Their technical decisions directly affected the privacy and safety of hundreds of students.

What Went Wrong

The most obvious vulnerability appeared in the profile URL. A user could change a link such as /profile/1048 to /profile/1049 and view another student’s record.

The server did not verify whether the logged-in user owned the requested profile or had permission to access it. This type of problem is commonly described as an insecure direct object reference or broken object-level authorization.

Violation of Complete Mediation

The principle of Complete Mediation requires the system to check authorization every time a protected resource is requested. Logging in is not enough.

Authentication answers the question, “Who is this user?” Authorization answers, “Is this user permitted to view this specific profile?”

The application checked that a person had an account but did not verify that the person was allowed to access the requested record. This means Complete Mediation was violated.

Violation of Fail-Safe Defaults

Fail-Safe Defaults means that access should be denied unless the system clearly confirms that permission exists.

In this application, users could access records unless something specifically blocked them. A secure system should do the opposite. It should deny access first and grant it only after completing a server-side authorization check.

Violation of Least Privilege

Every account reportedly had broad database read access. This violated the Principle of Least Privilege.

A normal member should only be able to access their own information and limited organization data. A treasurer may need to access payment records but may not need to view identification photos. An organization officer should not automatically gain access to another organization’s membership records.

The application’s database account should also have had restricted permissions instead of broad access to every table and record.

Violation of Defense in Depth

Defense in Depth means using several independent security layers. When one layer fails, another safeguard should reduce the damage.

The platform lacked secure transport, proper authorization, limited database permissions, protected secrets, safe error handling, and production security controls. Because many layers failed at the same time, one simple URL change exposed private information.

Violation of Secure by Default

The system used broad access permissions, full debugging messages, exposed credentials, and plain HTTP. These may be convenient settings during development, but they are unsafe for production.

A production system should disable stack traces, restrict access, require encrypted connections, protect session cookies, and deny unauthorized requests automatically.

Violation of Open Design

The developers assumed that users would not discover the internal URL format. This relied on secrecy instead of real authorization.

Secure design should remain safe even when users understand how the routes and application structure work. The URL format does not need to remain secret. Passwords, API keys, session secrets, and cryptographic keys must remain secret.

Violation of Secure Failure

Error pages displayed full stack traces. This may reveal internal file paths, database details, framework versions, environment settings, and application structure.

A public error message should only provide a simple explanation and a request identifier. Full technical details should be placed in protected logs accessible only to authorized developers.

Horizon One: Short-Term Containment

The first goal is to stop further exposure. New features should be paused until the system is secured and the possible breach is understood.

1. Take the Application Offline

Pulling the platform offline was an appropriate first step. The system should remain unavailable until unauthorized access paths are corrected.

Logs, database backups, hosting records, repository history, and configuration files should be preserved. These may show which records were accessed and whether the vulnerability was used.

This action restores Fail-Safe Defaults because access is denied while the system’s security is uncertain.

2. Rotate Exposed Credentials

The database password and payment API key should be treated as compromised even when there is no visible evidence that someone used them.

  • Disable the exposed database account.
  • Create a new account with limited access.
  • Revoke and regenerate the payment API key.
  • Rotate session and application secrets.
  • Invalidate active user sessions.
  • Review database and payment-provider logs.

Removing a password from the latest GitHub file is not enough because it may remain visible in earlier commits. The secret must be revoked first.

These actions restore Least Privilege, Compartmentalization, and Defense in Depth.

3. Fix Authorization Checks

Every request involving personal information must pass through a server-side authorization check.

Before showing a profile, the application should verify that the requester is properly authenticated and has a legitimate relationship with the requested record.

The system should return a generic forbidden or not-found response when the requester lacks permission.

This restores Complete Mediation, Least Privilege, and Fail-Safe Defaults.

4. Require HTTPS

The system should only be available through HTTPS. HTTP requests should redirect automatically to an encrypted connection.

Session cookies should use Secure, HttpOnly, and appropriate SameSite settings. Debugging mode should also be disabled.

This restores Defense in Depth and Security by Default.

5. Investigate the Incident

The team should identify the information affected, the period during which the vulnerability existed, and the users who may have accessed records they did not own.

They should also determine whether private files, payment details, identification photos, and chat messages were exposed through other routes.

It is not enough to say that nothing malicious happened. The absence of a complaint does not prove that unauthorized access did not occur.

6. Follow Data Breach Procedures

The team should immediately involve the university’s Data Protection Officer or authorized privacy personnel.

Under Republic Act No. 10173, organizations handling personal information must apply reasonable organizational, physical, and technical security measures.

A documented breach assessment should determine whether notification to the National Privacy Commission and affected data subjects is required.

This restores Accountability, Transparency, and responsible incident handling.

Horizon Two: Long-Term Design Changes

Containment addresses the immediate danger. Long-term improvements are needed to prevent the same security conditions from returning.

1. Begin With Security and Privacy Requirements

Before rebuilding the system, the developers should identify all user roles, personal data fields, access boundaries, legal obligations, misuse cases, and possible attacks.

Security requirements should be treated as core product requirements instead of optional features added at the end.

This restores Security by Design.

2. Collect Less Personal Information

The team should review whether every requested data field is truly necessary.

For example, the platform may not need to retain a complete GCash screenshot. A transaction reference number, amount, payment date, and verification status may be sufficient.

Uploaded identification photos should only be collected when they are necessary for a specific and declared purpose. They should not be stored indefinitely.

These actions restore Data Minimization, Proportionality, and Privacy by Default.

3. Use Centralized Authorization

Authorization rules should be placed in one consistent system, such as middleware or a tested policy module.

The platform should verify role, record ownership, organization membership, and the sensitivity of the requested information.

Automated tests should confirm that one user cannot access another user’s profile or another organization’s records.

This restores Complete Mediation, Least Privilege, and Separation of Duties.

4. Separate Development and Production

Development, testing, and production environments should use different databases, accounts, API keys, and hosting settings.

Real student data should not be copied into a development environment without a legitimate reason and proper protection.

Secrets should be stored in protected environment variables or secret-management services rather than being placed directly inside source code.

This restores Compartmentalization and Defense in Depth.

5. Protect Data in Transit and at Rest

HTTPS should be mandatory. Sensitive files should be stored privately and should only be accessed through authorized requests.

Backups should be encrypted, protected, tested, and included in the platform’s deletion and retention policy.

Passwords should be stored using secure password hashing rather than plain text or reversible encryption.

6. Create a Secure Development Process

Every release should undergo human code review, authorization tests, dependency scanning, secret scanning, static security testing, dynamic testing, and privacy review.

Logging should record important authentication and authorization events without unnecessarily copying sensitive information into log files.

This creates repeatable protection instead of relying only on developer memory.

7. Treat AI-Generated Code as Untrusted

Artificial intelligence coding assistants can generate working code quickly, but working code is not automatically secure code.

AI-generated code should be reviewed in the same way as code copied from an unknown internet source. It must be tested, verified, threat-modeled, and compared with the project’s security requirements.

An AI assistant may generate a working profile endpoint but fail to include access control, safe logging, rate limiting, secure database permissions, privacy controls, or proper error handling.

The developers remain responsible for the final system and its consequences.

Obligations Under RA No. 10173

Republic Act No. 10173, also known as the Data Privacy Act of 2012, requires personal information to be processed according to transparency, legitimate purpose, and proportionality.

Developers influence whether these principles are actually followed. Their architecture determines who can view the data, how long the information is retained, whether access is recorded, and whether unauthorized disclosure is prevented.

Privacy is therefore not only the responsibility of legal officers or university administrators. It is reflected in database permissions, access-control policies, file-storage settings, error messages, encryption, and deletion procedures.

Shipping Fast Without Sacrificing Trust

Speed is valuable. Hackathons and AI coding assistants allow small teams to turn ideas into working prototypes quickly. However, the acceptable level of risk changes when a prototype begins accepting real users and real personal information.

There should be a clear boundary between demonstration software and production software. Before crossing that boundary, a team must assess the information it will hold, establish proper access control, protect credentials, minimize data collection, require encrypted connections, test the system, and prepare an incident-response plan.

A platform is not truly successful simply because it was completed in 72 hours. It is successful when it works while also respecting the privacy, security, and dignity of the people who use it.

AI can accelerate programming, but it cannot replace human judgment, professional responsibility, and accountability. The faster software is produced, the more disciplined its review must become.

Build quickly, but never treat real people and their personal information as testing material.
